# 코드 리뷰 가이드

코드 리뷰의 목적은 취향을 통일하는 것이 아니라 오류와 위험을 병합 전에 찾고, 변경 의도를 함께 이해하는 것입니다.

## 리뷰 순서

1. PR의 변경 이유와 범위를 읽습니다.
2. CI가 통과했는지 확인합니다.
3. 사용자 동작, 데이터 흐름, 인증과 보안을 먼저 봅니다.
4. 테스트가 중요한 실패 경로를 다루는지 확인합니다.
5. 마지막으로 이름, 구조, 중복과 가독성을 봅니다.

## 코멘트 수준

심각도는 네 단계를 씁니다. AI 통합 코멘트가 두 리뷰어의 심각도를 이 네 단계로 정규화해 섹션을 나누므로, 사람이 쓰는 코멘트도 같은 말을 쓰는 편이 읽기 쉽습니다.

| 표식 | 통합 코멘트 | 뜻 |
| --- | --- | --- |
| **critical:** | 🔴 반드시 수정 | 병합 전에 반드시 해결해야 하는 오류, 보안 문제, 데이터 손실 위험 |
| **major:** | 🟠 수정 권장 | 회귀 가능성이나 유지보수 문제처럼 해결을 강하게 권장하는 항목 |
| **minor:** | 🟡 개선 제안 | 더 나은 대안이지만 작성자가 선택할 수 있는 개선안 |
| **nit:** | ⚪ 사소함 | 오타나 표기처럼 고쳐도 그만인 항목 |

심각도가 아닌 코멘트에는 다음 표식을 씁니다. 통합 코멘트에는 대응하는 섹션이 없습니다.

- **question:** 의도나 전제 조건을 확인하는 질문
- **praise:** 유지하면 좋은 설계나 구현

## 좋은 리뷰 코멘트

- 한 코멘트에는 한 가지 문제만 다룹니다.
- 문제가 발생하는 조건과 사용자 영향을 함께 적습니다.
- 가능하면 수정 방향이나 GitHub suggestion을 제시합니다.
- 근거 없이 개인 취향만 강제하지 않습니다.
- 범위 밖의 개선은 현재 PR을 막는 대신 후속 이슈로 분리합니다.

```text
critical: 인증되지 않은 요청에서도 이 분기가 실행되어 다른 사용자의 기록을 읽을 수 있습니다.
서버에서 사용자 ID를 먼저 확인하고, 조회 조건에도 해당 ID를 포함해 주세요.
```

## 혼자 개발할 때

PR 작성자가 자신의 PR을 승인할 수는 없으므로 승인 1개를 필수 조건으로 두지 않습니다. 대신 아래 항목을 병합 조건으로 사용합니다.

- `PR title`과 `Quality` CI 통과
- 모든 리뷰 대화 해결
- draft 해제 전 `Review focus` 작성
- 중요한 변경은 PR 링크와 함께 별도 코드 리뷰 요청

AI 리뷰를 요청할 때는 “전체적으로 봐줘”보다 다음처럼 범위를 명확히 지정하는 편이 좋습니다.

```text
이 PR에서 correctness, 보안, 회귀 가능성을 우선 검토하고
실제 수정이 필요한 내용만 파일과 줄 번호를 붙여 코멘트해 줘.
```

## 자동 AI 리뷰

PR을 열거나 커밋을 푸시하면 `AI Review` 워크플로가 리뷰를 요청하고, 결과를 하나의 PR 코멘트로 합칩니다. draft 여부와 무관하게 동작합니다. 포크에서 올라온 PR은 시크릿이 전달되지 않으므로 건너뜁니다.

목표는 PR에 남는 리뷰 코멘트를 통합 코멘트 하나로 두는 것입니다. 그래서 리뷰어를 하나만 돌리고, 원본 코멘트는 지울 수 있는 만큼 지웁니다.

- 평소에는 **CodeRabbit 하나만** 요청합니다. 리뷰어를 늘리면 실행이 길어지고, 삭제할 수 없는 리뷰 본문이 리뷰어 수만큼 회색 줄로 남습니다.
- **Codex는 폴백입니다.** CodeRabbit 이 성공하지 못하면(할당량, 요청 실패, 타임아웃 구분 없이) 그때 Codex 를 부릅니다. 폴백을 탄 실행은 두 리뷰가 직렬로 돌아 최대 20분까지 걸립니다.
- 리뷰어는 자기네 서버에서 돕니다. CI는 요청만 남기고 결과는 GitHub API로 걷어옵니다. 우리가 별도로 호출하는 API가 없으므로 플랜 한도 안에서는 추가 요금이 붙지 않습니다. 다만 한도를 넘긴 뒤에는 각 서비스 설정에 따라 과금될 수 있습니다. CodeRabbit은 usage-based reviews를 켜 두면 파일당 요금이 붙고, Codex는 한도 초과 시 크레딧을 씁니다.
- 통합 코멘트가 올라간 뒤, **원본 인라인 코멘트와 잡음 코멘트는 삭제합니다.** 접기로는 부족했습니다. 접힌 인라인은 Files changed 탭에 파일마다 회색 줄로 남고, 접어도 스레드는 해소되지 않아 "unresolved conversations" 배너가 그대로 뜹니다.
- **삭제는 되돌릴 수 없습니다.** 지적 원문과 코드 위치 링크는 통합 코멘트가 들고 있지만, 파서가 리뷰어의 출력 형식 변경으로 깨지면 통합 코멘트에도 내용이 실리지 않고 원본은 이미 지워진 뒤입니다. `ai-review-raw` 아티팩트는 이름과 달리 파싱을 마친 결과만 담고 있어 이 경우의 복구 경로가 되지 못합니다. 파싱이 깨졌는지 알아채려면 통합 코멘트에 위치만 있고 내용이 빈 항목이 보이는지 확인합니다.
- 리뷰 이벤트 본문(CodeRabbit "Actionable comments posted: N")은 삭제 API가 없어 접기만 합니다. 실행마다 회색 한 줄이 남는 것이 현재 한계입니다.
- 수확이 실패한 실행에서는 인라인을 지우지 않습니다. 통합 코멘트에 지적이 실리지 않은 채 원본까지 지우면 리뷰가 통째로 사라지기 때문입니다.
- 이번 실행이 수확하지 못한 지적은 원본을 지우기 전에 통합 코멘트로 옮기고, 현재 결과와 섞지 않습니다. 같은 SHA에서 먼저 끝난 리뷰의 지적은 **"같은 커밋의 이전 리뷰에서 온 지적"**, 이전 SHA에 달린 지적은 **"이전 커밋에서 온 지적"** 섹션에 각각 접어서 싣습니다.
- 수확 완료 로그의 전체 지적 수에는 이 두 이전 결과가 포함되며, 괄호 안에 포함 건수가 따로 표시됩니다. 통합 코멘트 헤더의 리뷰 건수는 현재 라운드에서 수확한 지적만 세고, 두 접기 섹션의 지적은 제외합니다.
- 리뷰가 실패하면 사유가 통합 코멘트 헤더에 표시됩니다.

재검토가 필요하면 커밋을 푸시합니다. 워크플로가 `pull_request`의 `opened`, `synchronize`, `reopened`만 구독하므로, 커밋 없이 `@codex review`나 `@coderabbitai review`를 직접 남기면 앱은 리뷰하지만 워크플로가 돌지 않습니다. 그 결과는 통합 코멘트에 합쳐지지도, 지워지지도 않고 원본 코멘트로 남습니다. 커밋을 더할 상황이 아니면 Actions에서 `AI Review` 실행을 재실행합니다.

리뷰 요청은 `enzy-won` 계정 토큰으로 보냅니다. 구독 귀속이 명확해야 하기 때문입니다. 저장소 관리자가 다음 설정을 한 번 완료해야 합니다.

1. `enzy-won` 계정에서 Fine-grained personal access token을 만듭니다.
2. Resource owner는 `enzywon` 조직, 접근 저장소는 `gachi-bollae` 하나만 선택합니다.
3. Repository permissions에서 `Issues: Read and write`만 추가합니다. GitHub는 PR의 일반 댓글을 Issue comment로 처리합니다. 인라인 코멘트 삭제는 Actions 토큰으로 하므로 이 토큰에 `Pull requests` 권한은 주지 않습니다. Actions 토큰이 막히면 삭제 재시도도 실패하는데, 그때는 원본 코멘트가 남을 뿐 리뷰 결과는 통합 코멘트에 그대로 실립니다.
4. 저장소의 `Settings > Secrets and variables > Actions`에 `ENZY_WON_CODEX_REVIEW_TOKEN` 이름으로 저장합니다.

토큰은 파일이나 PR에 입력하지 않습니다. 만료일을 설정하고, 만료되거나 폐기한 뒤에는 같은 이름의 Secret만 교체합니다. 이 Secret이 없으면 워크플로는 Actions 토큰으로 리뷰를 요청하지만, 구독 귀속이 흐려집니다.

협업자가 생기면 `.github/CODEOWNERS`를 추가하고 영역별 담당자에게 리뷰가 자동 요청되도록 확장합니다.
