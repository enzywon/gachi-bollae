# 같이볼래 — 디자인 적용 계획

## 1. 문서 정보

- 문서 버전: v0.1
- 작성일: 2026년 8월 9일
- 대상 제품: 같이볼래 (gachi-bollae)
- 대상 범위: 기존 프로토타입에 서비스 디자인 방향을 적용하는 계획
- 상위 문서: [서비스 디자인 컨셉](./gachi-bollae-service-design-concept-v0.1.md)
- 관련 문서: [함께 보기 MVP UX 명세](./gachi-bollae-together-mvp-ux-v0.1.md)

### 1.1 이 문서의 역할

이 문서는 새로운 제품 요구사항을 정의하는 PRD가 아니다.
이미 구현된 1차 프로토타입을 기준으로, 실제 서비스 출시를 염두에 둔 디자인 방향을 어떻게 입힐지 정리한다.

따라서 이 문서는 다음 질문에 답한다.

- 현재 화면은 어떤 구조와 인상을 갖고 있는가?
- 서비스 컨셉과 현재 UI 사이의 차이는 무엇인가?
- 어떤 디자인 방향으로 조정해야 함께 보기 서비스로 더 선명해지는가?
- 구현은 어떤 순서로 쪼개는 것이 좋은가?

### 1.2 전제

- 현재 소스의 추천 흐름은 유지한다.
- 1차 산출물은 이미 있는 프로토타입이다.
- 이번 단계는 기능 확장보다 디자인 적용과 UX 정돈이다.
- 추천 알고리즘, 데이터 연동, 계정 구조는 별도 작업으로 분리한다.

## 2. 현재 화면 진단

### 2.1 현재 강점

현재 프로토타입은 다음 장점을 갖고 있다.

- 추천 흐름이 명확하다: 모드 → 상황 → 취향 → 조건 → 결과.
- 함께 보기 모드가 이미 존재한다.
- 각자 취향 입력 구조가 있다.
- 피하고 싶은 요소를 제외하는 안전 장치가 있다.
- 추천 결과에 이유가 표시된다.
- 선택 후 기록과 평가로 이어지는 흐름이 있다.
- 전체적으로 데모 서비스 이상의 완성감을 가진다.

### 2.2 현재 인상

현재 UI는 어두운 배경, 글래스 카드, 퍼플/코랄 그라데이션, 큰 히어로 타이포그래피를 중심으로 구성되어 있다.
첫인상은 감성적이고 엔터테인먼트 서비스답지만, 실제 선택 도구로서는 장식과 분위기가 기능보다 앞서는 구간이 있다.

### 2.3 컨셉 대비 차이

| 영역 | 현재 상태 | 디자인 적용 방향 |
| --- | --- | --- |
| 첫 화면 | 감성적 히어로와 모드 카드 중심 | 함께 보기 주 액션을 더 빠르게 인지 |
| 컬러 | 퍼플 계열이 강하게 지배 | 따뜻한 포인트는 유지하되 기능 영역은 더 차분하게 |
| 카드 | 큰 반경과 글래스 효과가 많음 | 반복 카드와 도구 영역은 더 단정하게 |
| 진행 흐름 | 단계는 명확하나 질문의 무게가 큼 | 3분 안에 끝나는 가벼운 진행감 강화 |
| 추천 결과 | 포스터형 카드가 매력적 | 비교와 결정에 필요한 정보 위계 강화 |
| 기록 | 저장 기능은 있음 | 다음 추천의 재료라는 메시지 강화 |

## 3. 디자인 방향

### 3.1 제품 인상

같이볼래는 "감성적인 추천 앱"보다 "둘이 빠르게 합의하게 도와주는 콘텐츠 선택 도구"에 가까워야 한다.

목표 인상은 다음과 같다.

- 친근하지만 가볍게만 보이지 않는다.
- 귀엽지만 선택 흐름을 방해하지 않는다.
- 추천 결과를 탐색하게 하기보다 결정하게 돕는다.
- 둘 중 한 사람의 취향이 밀린다는 느낌을 주지 않는다.

### 3.2 시각 원칙

#### 장식은 줄이고 신호는 키운다

배경 장식과 큰 그라데이션은 첫 화면의 분위기 형성에는 도움이 된다.
다만 입력 단계와 결과 단계에서는 사용자가 선택해야 하는 정보가 먼저 보여야 한다.

#### 카드 반경과 깊이를 정돈한다

현재 `mode-card`, `context-card`, `result-card`는 모두 큰 반경과 강한 그림자를 사용한다.
출시용 UI에서는 다음 기준으로 정리한다.

- 주요 선택 카드: 16-20px
- 결과 카드: 14-18px
- 칩과 작은 버튼: 999px 허용
- 기록 목록 카드: 12-16px

#### 퍼플을 브랜드 포인트로 낮춘다

퍼플/코랄은 브랜드 포인트로 유지한다.
하지만 전체 화면을 지배하는 색이 되면 도구보다 이벤트 페이지처럼 보일 수 있다.

권장 방향:

- 배경은 더 차분한 딥 네이비 또는 차콜 기반
- 주요 CTA에 퍼플/코랄 사용
- 성공, 기록, 안전 정보에는 별도 색상 사용
- 추천 결과 정보 영역은 대비와 가독성 우선

#### 콘텐츠 시각 요소를 더 명확히 한다

현재 데모 포스터는 시각적 완성도는 있으나 실제 콘텐츠를 inspect하는 용도는 약하다.
실제 서비스 전환을 염두에 두면 결과 카드의 이미지는 다음 중 하나로 정리한다.

- 실제 포스터 이미지
- 포스터 이미지가 없을 때의 일관된 fallback
- 장르/무드 기반 색상 fallback

## 4. 화면별 적용 계획

### 4.1 첫 화면

#### 목표

사용자가 들어오자마자 "이 서비스는 둘이 볼 것을 정해준다"라고 이해해야 한다.

#### 현재 조정 포인트

- 현재 헤드라인은 감성적이지만 서비스 목적이 약간 늦게 읽힌다.
- `함께 볼게요`가 주 버튼이지만 `혼자 볼게요`와 같은 카드 레벨로 놓여 있다.
- 빠른 상황 예시는 좋지만, 함께 보기 문제를 직접 보여주지는 않는다.

#### 적용 방향

- H1을 서비스 가치에 더 직접적으로 맞춘다.
- `함께 볼게요`를 단일 주 CTA로 더 크게 둔다.
- `혼자 볼게요`는 텍스트 버튼 또는 보조 카드로 낮춘다.
- 대표 상황은 "식사 중", "자기 전" 같은 맥락 신호로 유지한다.
- 첫 화면에서 함께 본 목록은 상단 보조 링크로 유지한다.

#### 예시 카피

| 요소 | 현재 | 제안 |
| --- | --- | --- |
| H1 | 지금, 함께 보기 좋은 콘텐츠 | 둘이 오늘 볼 콘텐츠를 3분 안에 |
| 보조 문구 | 상황과 취향을 맞춰 3분 안에 골라드려요. | 상황과 각자 취향을 맞춰, 둘 다 납득할 후보만 좁혀드려요. |
| 주 CTA | 함께 볼게요 | 함께 골라볼게요 |
| 보조 CTA | 혼자 볼게요 | 혼자 고르기 |

---

### 4.2 상황 선택

#### 목표

상황 선택이 단순 취향 질문이 아니라 실패 가능성을 줄이는 첫 필터라는 점을 전달한다.

#### 현재 조정 포인트

- 상황 카드의 아이콘과 힌트는 충분히 명확하다.
- 카드 크기가 커서 모바일에서 단계가 길게 느껴질 수 있다.
- 기본 제외 요소가 적용되는 이유가 작게만 드러난다.

#### 적용 방향

- 카드 높이를 줄이고 스캔성을 높인다.
- 선택된 상황 아래에 적용된 제외 요소를 작은 안내로 보여준다.
- `상황을 선택하면 피하고 싶은 요소도 먼저 챙겨드려요` 카피는 유지 가능하다.

#### 구현 단위

- `context-card` 높이와 내부 간격 조정
- 선택 상태의 안내 배지 추가
- 모바일 2열 또는 1열 전환 기준 점검

---

### 4.3 무드와 각자 취향

#### 목표

두 사람의 취향이 공평하게 반영된다는 느낌을 만든다.

#### 현재 조정 포인트

- `나의 취향`, `파트너 취향` 구조는 기능적으로 적절하다.
- `파트너` 표현은 관계를 특정할 수 있다.
- 취향을 여러 개 선택할 수 있지만 권장 개수나 선택 부담 완화가 없다.

#### 적용 방향

- `파트너 취향`을 `같이 보는 사람 취향`으로 바꾼다.
- 두 취향 패널의 시각적 무게를 같게 둔다.
- 1-3개 권장 문구를 작은 보조 텍스트로 제공한다.
- 무드와 장르의 관계를 더 명확히 구분한다.

#### 예시 카피

| 요소 | 제안 |
| --- | --- |
| 단계 제목 | 오늘은 어떤 느낌으로 볼까요? |
| 나의 취향 | 내가 끌리는 장르 |
| 상대 취향 | 같이 보는 사람이 끌리는 장르 |
| 도움 문구 | 각자 1-3개만 골라도 충분해요. 겹치는 지점부터 찾아볼게요. |

---

### 4.4 조건 필터

#### 목표

오늘 실제로 볼 수 있는 조건을 빠르게 확정한다.

#### 현재 조정 포인트

- 시간, 형식, OTT, 회피 요소가 한 화면에 잘 모여 있다.
- `필수 조건은 추천할 때 절대 임의로 해제하지 않아요`는 좋은 신뢰 문구다.
- OTT가 단일 선택이라 실제 사용자 기대와 다를 수 있지만, 이번 디자인 적용 범위에서는 유지한다.

#### 적용 방향

- 조건 영역을 더 도구처럼 차분하게 만든다.
- `상관없음`이 의도적인 허용 선택임을 명확히 한다.
- 회피 요소 영역은 안전 조건으로 시각적으로 구분한다.

#### 구현 단위

- 필터 카드의 시각 강도 낮추기
- 회피 요소 선택 상태 안내 강화
- 결과 화면 조건 요약과 연결

---

### 4.5 추천 결과

#### 목표

사용자가 3개 후보를 비교하고 하나를 고르게 만든다.

#### 현재 조정 포인트

- 결과 카드는 시각적으로 풍부하다.
- 포스터 영역이 커서 정보 비교가 아래로 밀린다.
- `함께 만족` 퍼센트가 강하지만 사용자가 근거를 알기 어렵다.
- 추천 이유는 있으나 두 사람 취향 균형을 더 직접적으로 설명할 수 있다.

#### 적용 방향

- 결과 카드에서 `제목`, `시간`, `OTT`, `추천 이유`, `선택 버튼`의 우선순위를 높인다.
- 포스터 영역은 유지하되 높이를 줄이거나 카드 정보와 균형을 맞춘다.
- 퍼센트는 유지한다면 근거가 있는 숫자처럼 보이게 하고, 아니면 문장형 배지로 바꾼다.
- 추천 이유는 상황, 취향 균형, 회피 요소 중 최소 2개를 보여준다.

#### 추천 이유 디자인

추천 이유는 긴 설명보다 짧은 칩 또는 체크 리스트가 적합하다.

예:

- 식사 중 보기 편해요
- 둘 다 고른 코미디 취향 반영
- 피하고 싶은 공포 요소 없음

#### 액션 우선순위

| 우선순위 | 액션 | 디자인 |
| --- | --- | --- |
| 1 | 이걸 볼게요 | 강한 CTA |
| 2 | 다른 3개 보기 | 결과 하단 보조 CTA |
| 3 | 조건 수정 | 상단 보조 CTA |
| 4 | 별로예요, 이미 봤어요 | 작은 보조 액션 |

---

### 4.6 선택 완료와 기록

#### 목표

선택이 끝난 뒤 사용자가 시청과 기록으로 자연스럽게 이어지게 한다.

#### 현재 조정 포인트

- 선택 배너와 기록 버튼이 이미 있다.
- 기록이 다음 추천의 재료라는 의미는 아직 약하다.

#### 적용 방향

- 선택 완료 배너에서 "기록하면 다음 추천에 참고한다"는 메시지를 추가한다.
- 기록 버튼은 강요처럼 보이지 않게 둔다.
- 저장 성공 토스트는 `기록 보러 가기`와 `계속 추천 보기`를 명확히 나눈다.

#### 예시 카피

- 이 콘텐츠로 결정했어요.
- 다 보고 나면 별점만 남겨도 다음 추천에 참고할게요.
- 기록을 저장했어요. 다음에 둘이 고를 때 참고할 수 있어요.

---

### 4.7 함께 본 목록

#### 목표

기록 목록을 단순 보관함이 아니라 재방문 루프로 만든다.

#### 현재 조정 포인트

- 목록, 미평가 안내, 필터, 수정/삭제 기능이 있다.
- 다시 추천받는 맥락은 상단 링크에만 있다.

#### 적용 방향

- 목록 상단에 재추천 진입 메시지를 둔다.
- 미평가 안내는 부담보다 가벼운 후속 작업처럼 보이게 한다.
- 시청 맥락이 있는 기록은 추천 학습 재료처럼 표시한다.

#### 예시 카피

- 지난번에 좋았던 선택을 바탕으로 다시 골라볼까요?
- 별점은 나중에 남겨도 괜찮아요.
- 이 기록은 `식사 중`, `함께 보기` 추천에서 저장됐어요.

## 5. 추천 흐름에 대한 의견

현재 추천 흐름은 데모이므로, 그대로 다듬는 것보다 실제 서비스에서 더 설득력 있는 흐름으로 바꿀 여지가 있다.
아래 의견은 당장 모두 구현해야 할 요구사항이 아니라, 디자인 적용 과정에서 검토할 방향이다.

### 5.1 함께 보기에서는 모드 선택을 없애도 된다

현재 첫 화면은 `혼자 볼게요`와 `함께 볼게요`를 나란히 보여준다.
하지만 서비스 방향이 함께 보기 중심이라면 첫 화면에서 모드를 고르게 하는 것은 핵심 메시지를 흐릴 수 있다.

권장안:

- 기본 흐름은 `함께 골라볼게요` 하나로 시작한다.
- `혼자 고르기`는 상단 또는 하단의 보조 링크로 둔다.
- 첫 화면의 질문은 `누구와 볼까요?`보다 `오늘 둘이 어떤 걸 볼까요?`에 가깝게 바꾼다.

이렇게 하면 사용자가 이 서비스를 "혼자 추천도 되고 같이 추천도 되는 앱"이 아니라 "같이 고를 때 쓰는 앱"으로 이해한다.

### 5.2 질문 순서는 `상황 → 시간 → 취향`도 검토할 만하다

현재 흐름은 `상황 → 무드/취향 → 조건`이다.
실제 함께 보기에서는 취향보다 시간이 먼저 결정되는 경우가 많다.

예:

- 밥 먹는 동안 볼 것인가?
- 자기 전 30분만 볼 것인가?
- 주말에 2시간짜리 영화를 볼 수 있는가?

권장안:

```text
상황 선택 → 볼 수 있는 시간 선택 → 각자 취향 선택 → 피하고 싶은 요소 확인 → 결과
```

이 흐름의 장점은 초반에 후보 범위를 현실적으로 줄인다는 점이다.
단점은 현재 구현보다 단계 재배치가 필요하다는 점이다.

디자인 적용 1차에서는 현재 순서를 유지해도 되지만, 실제 출시 전 사용성 테스트에서는 이 순서도 비교해야 한다.

### 5.3 무드는 필수 질문이 아닐 수 있다

현재는 무드를 반드시 1개 선택해야 다음으로 넘어간다.
하지만 함께 보는 상황에서는 무드보다 `싫은 것 피하기`가 더 강한 의사결정 요소일 수 있다.

권장안:

- 무드는 필수에서 선택 입력으로 낮춘다.
- 대신 `피하고 싶은 요소`를 더 앞 단계에서 가볍게 확인한다.
- 무드를 고르지 않으면 추천 이유에서 무드 관련 문장을 생략한다.

이렇게 하면 사용자가 억지로 감정을 고르는 부담이 줄어든다.
특히 "그냥 밥 먹으면서 볼 것"을 찾는 사용자는 무드 선택이 불필요하게 느껴질 수 있다.

### 5.4 각자 취향 입력은 `나/상대`보다 `A/B`가 나을 수 있다

`나의 취향`, `파트너 취향`은 이해하기 쉽지만 한 기기를 같이 볼 때는 누가 먼저 입력하는지 애매할 수 있다.
관계 유형도 커플에 한정되는 인상을 줄 수 있다.

권장안:

- `첫 번째 사람`, `두 번째 사람`
- `내가 고르기`, `같이 보는 사람이 고르기`
- 추후 페어 프로필이 생기면 사용자가 이름을 직접 붙이게 한다.

1차 디자인 적용에서는 `같이 보는 사람 취향` 정도로만 바꿔도 충분하다.

### 5.5 결과는 3개보다 `대표 1개 + 대안 2개`가 더 결정에 강하다

현재는 3개 카드가 같은 위계로 노출된다.
하지만 서비스 목표가 탐색이 아니라 합의라면, 결과를 모두 같은 무게로 보여주는 방식은 결정을 다시 사용자에게 넘길 수 있다.

권장안:

- 1번 후보를 `오늘의 추천`으로 크게 보여준다.
- 2번과 3번은 `조금 더 가벼운 선택`, `더 몰입하는 선택` 같은 대안으로 보여준다.
- 각 후보의 차이를 명확히 설명한다.

예:

| 후보 | 역할 |
| --- | --- |
| 오늘의 추천 | 두 사람 취향과 상황이 가장 균형 잡힌 선택 |
| 가벼운 대안 | 더 짧고 부담 없는 선택 |
| 몰입 대안 | 시간이 있을 때 더 만족할 수 있는 선택 |

이 방식은 디자인 변경 폭이 크지만, 같이볼래의 "빠른 합의" 컨셉에는 더 잘 맞는다.

### 5.6 `별로예요`보다 구체적인 거절 이유가 더 가치 있다

현재 결과 카드에는 `별로예요`가 있다.
데모에서는 충분하지만 실제 서비스에서는 왜 별로인지 알아야 다음 추천과 UX가 좋아진다.

권장안:

- `너무 길어요`
- `지금 분위기랑 안 맞아요`
- `이미 봤어요`
- `취향이 아니에요`
- `너무 무거워요`

단, 1차 디자인 적용에서는 버튼을 늘리지 않는다.
대신 `별로예요`를 누른 뒤 작은 이유 선택 시트를 여는 방향을 후속 후보로 둔다.

### 5.7 기록은 추천 이후가 아니라 서비스 루프의 일부로 보여야 한다

현재 기록은 선택 후 평가 기능에 가깝다.
실제 서비스에서는 기록이 있어야 "우리 둘에게 맞는 추천"이라는 기대가 생긴다.

권장안:

- 첫 화면 또는 함께 본 목록에 `지난 선택을 참고해서 고르기` 진입을 둔다.
- 기록 저장 성공 문구에서 다음 추천 개선을 명확히 말한다.
- 추천 결과에서 이미 본 콘텐츠는 별도 처리한다.

이 방향은 데이터 연동이 필요하므로 바로 구현하지 않아도 된다.
하지만 디자인 메시지는 지금부터 맞춰 두는 것이 좋다.

### 5.8 1차 디자인 적용에서 반영할 의견

이번 단계에서 바로 반영하기 좋은 항목은 다음이다.

| 반영 여부 | 항목 | 이유 |
| --- | --- | --- |
| 반영 | 함께 보기 CTA를 주 액션으로 강화 | 서비스 컨셉이 바로 선명해짐 |
| 반영 | `파트너 취향` 표현 완화 | 관계 유형을 좁히지 않음 |
| 반영 | 결과 카드 추천 이유 개선 | 선택 납득에 직접 영향 |
| 반영 | 선택/기록 카피 개선 | 재방문 루프의 의미 강화 |
| 보류 | 질문 순서 재배치 | 구현 영향이 있어 테스트 후 결정 |
| 보류 | 무드 선택 optional 전환 | 추천 로직과 결과 문구 영향 |
| 보류 | 대표 1개 + 대안 2개 결과 구조 | 카드 레이아웃 재설계 필요 |
| 보류 | 거절 이유 수집 | 상태와 데이터 설계 필요 |

## 6. 컴포넌트 적용 기준

### 6.1 버튼

- 주 CTA는 화면당 하나만 둔다.
- 보조 액션은 테두리 버튼 또는 텍스트 버튼으로 낮춘다.
- `이전`, `처음부터`, `조건 수정`은 주 CTA와 경쟁하지 않게 한다.

### 6.2 카드

- 선택 카드와 결과 카드는 기능이 다르므로 같은 시각 강도를 쓰지 않는다.
- 선택 카드는 빠른 스캔과 탭 영역을 우선한다.
- 결과 카드는 비교 가능한 정보 위계를 우선한다.
- 기록 카드는 반복 목록이므로 더 조용해야 한다.

### 6.3 칩

- 칩은 장르, 무드, 회피 요소처럼 선택 가능한 옵션에 사용한다.
- 선택된 칩은 체크 표시와 색상 둘 다로 구분한다.
- 회피 요소 칩은 일반 취향 칩보다 더 신중한 톤을 사용한다.

### 6.4 텍스트

- 헤드라인은 첫 화면과 단계 제목에만 크게 쓴다.
- 카드 내부 제목은 작고 조밀하게 유지한다.
- 설명 문구는 사용자가 지금 해야 할 행동을 돕는 경우에만 둔다.

## 9. 검증 방법

디자인 적용 후에는 다음 방식으로 확인한다.

### 9.1 화면 확인

- 데스크톱 첫 화면
- 모바일 첫 화면
- 상황 선택
- 취향 선택
- 조건 필터
- 추천 결과
- 빈 결과
- 선택 완료 배너
- 기록 시트
- 함께 본 목록

### 9.2 사용성 체크

- 첫 화면에서 함께 보기 목적이 5초 안에 이해되는가?
- 주 CTA가 하나로 보이는가?
- 두 사람 취향 입력이 공평하게 보이는가?
- 결과 카드에서 제목, 시간, OTT, 추천 이유가 바로 읽히는가?
- 기록하기가 부담이 아니라 다음 선택을 위한 후속 행동으로 보이는가?

### 9.3 기술 확인

- `npm run lint`
- `npm test`
- 데스크톱/모바일 브라우저 스크린샷 확인
- 추천 결과가 없는 조건에서 빈 상태 확인
- 기록 저장 실패 상태 확인

## 10. 구현 PR 단위 제안

디자인 적용은 한 번에 크게 바꾸기보다 다음 PR 단위로 나누는 것이 좋다.

### PR 1: 첫 화면과 카피 정렬

- 첫 화면 헤드라인 변경
- 함께 보기 CTA 강조
- 혼자 보기 보조화
- 취향 입력 명칭 정리
- 선택/기록 카피 정리

### PR 2: 추천 결과 카드 정리

- 결과 카드 정보 위계 조정
- 추천 이유 문구 개선
- 포스터와 본문 비율 조정
- 빈 결과 안내 개선

### PR 3: 함께 본 목록 재방문 루프

- 목록 상단 재추천 메시지
- 미평가 안내 카피 개선
- 기록 맥락 표시 강화

### PR 4: 반응형과 시각 밀도 정리

- 카드 반경과 그림자 정리
- 모바일 레이아웃 점검
- 터치 영역과 텍스트 줄바꿈 확인

## 11. 결정 사항

- 지금 단계는 PRD 작성이 아니라 디자인 적용 계획 단계로 본다.
- 현재 소스의 기능 흐름은 유지한다.
- 함께 보기 경험을 첫 화면과 결과 화면에서 더 강하게 드러낸다.
- 퍼플/코랄 톤은 유지하되 화면 전체를 지배하지 않게 조정한다.
- 기록 기능은 다음 추천의 재료라는 의미를 더 분명히 한다.

## 12. 미결정 사항

- 첫 화면에서 `혼자 볼게요`를 카드로 유지할지 텍스트 버튼으로 낮출지
- `함께 만족` 퍼센트를 유지할지 문장형 배지로 바꿀지
- 포스터 영역의 높이를 얼마나 줄일지
- 실제 포스터 이미지가 들어오기 전까지 fallback을 현재 방식으로 유지할지
- 디자인 적용 PR을 한 번에 할지, PR 단위 제안처럼 나눌지
- 질문 순서를 유지할지 `상황 → 시간 → 취향`으로 바꿀지
- 무드를 필수 입력으로 유지할지 선택 입력으로 낮출지
- 결과를 동일 위계 3개로 둘지 `대표 1개 + 대안 2개` 구조로 바꿀지
